## 二、协作风格（观察所得，待确认）

### 2.1 沟通偏好
- **语言**：默认中文，英文术语后加中文注释（全局 CLAUDE.md 规则）
- **直接性**：表达直接，当执行偏离预期时会明确指出，偶尔使用强烈措辞表达不满
- **追问习惯**：要求 AI "继续质问我你不懂的东西"，倾向于通过质问和深挖来澄清需求，而非一次性给完整规格
- **验证驱动**：命中关键改动后要求验证，重视截图和实际数据反馈

### 2.2 对 AI 的期望
- **最小改动**：默认只做最小必要改动（全局 CLAUDE.md 规则）
- **先读后改**：非简单任务先读再改
- **复杂任务先 plan**：需要先获得方案确认再执行
- **规则执行力**：对硬规则（如"优先原线分配""达标即可"）要求原样执行，不接受 AI 自行演绎或模糊处理
- **根因修复**：不接受表面补丁，要求触及根因的修复

### 2.3 冲突点（需用户校准）
- **"不限制单场" vs "同等级要均衡"**：用户曾要求去掉 cap（"487 万就是要分干净"），但看到 B 级单场拿到 70w 时又认为不合理。当前理解为：**总库存要分完，单场可超目标，但不能以牺牲同线同等级其他直播为代价**。
- **对排期规则的理解权**：用户认为自己比 AI 更懂业务规则，当 AI "擅自解释规则" 时容易触发不满。当前策略是遇到规则争议先复述确认，再执行。

## 三、工作惯性（观察所得，待确认）

### 3.1 数据工作流
- **Excel 为核心载体**：排期表、audience 量级表、跨科偏好表、直播明细表均通过 Excel 上传
- **Vercel 部署**：前端静态托管，通过 `git push` + CLI 强制部署
- **浏览器验证为主**：上传文件 → 自动排期 → 截图反馈，形成闭环
- **状态重置依赖**：当 cloud / localStorage 出现旧数据污染时，需要一键重置并重新上传

### 3.2 决策模式
- **结果导向**：更关注分配结果是否符合业务直觉，而非算法优雅性
- **快速迭代**：接受多轮修正，但每次修正期望看到明显改善
- **历史经验敏感**：对过去踩过的坑（如 autoSchedule 连环 bug）记忆深刻，会在类似场景提前警惕

### 3.3 跨项目线索（轻量记录）
- 同时推进多个项目：AI 培训海报、App 商业化决策看板、直播排期看板等
- 角色可能不仅限于直播运营，还涉及 AI 应用统筹或运营策略规划（需确认）
