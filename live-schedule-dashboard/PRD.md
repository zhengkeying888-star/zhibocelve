# 直播排期策略看板 — 产品需求文档 (PRD)

> 版本：v2.3
> 日期：2026-05-13
> 适用范围：5月W2（5.11–5.17）及后续周次
> 关联仓库：`live-schedule-dashboard` + `schedule_solver.py`

---

## 1. 背景与目标

### 1.1 背景
私域直播运营团队每周需要完成大量直播排期工作。排期涉及：
- 确定一周内每天各时段的直播场次（含联合直播）
- 为每一场直播分配对应的 audience 人群（存量用户）
- 根据历史实际数据（4月直播明细表）校准 GMV 预估，避免理论模型虚高/低估
- 避免同一用户在短时间内被重复触达（频控）
- 人工调整经验无法被系统学习和复用

**v2.3 关键痛点**：原有 `crossRate × LTV` 理论模型对 4 月预测产值 56.8w，但剔除新量测试后实际日常排期产值约 80w，模型严重低估（约 29% 误差）；同时部分无历史数据的品类（如「朗诵」）理论预估虚高至 17.6w，实际从未直播过。

### 1.2 目标
构建一个**带智能体能力的直播排期策略看板**，让运营能够：
1. 上传现有排期 Excel，系统自动解析直播场次（含联合直播、伪直播）
2. 上传 audience 量级表，系统获得可分配的存量用户池
3. 上传跨科偏好数据，系统基于 cohortMonth 匹配历史跨科率 + LTV
4. **上传 4 月直播明细表，系统用实际历史 GMV 替换理论预估，动态缩放至 20–25w 目标区间**
5. 在看板上直观查看、编辑、校准排期结果
6. **拖拽调整 audience 分配，智能体记录原因并沉淀规则，下次自动优先应用**
7. 一键导出排期结果回 Excel
8. **云端同步**：多设备状态实时同步，配置永不丢失

---

## 2. 用户画像

- **主要用户**：私域直播运营团队（排期负责人）
- **使用频率**：每周 1-2 次（周度排期）
- **技术背景**：熟练使用 Excel，不需要编程能力
- **核心痛点**：
  - Excel 排期效率低，跨表数据难以联动
  - 不知道每个直播该分配哪个 audience 人群
  - 无法按进量月份精细化预估跨科率和 GMV
  - 容易违反频控规则（3天/当日去重）
  - 人工调整经验无法被系统学习和复用
  - 多人/多设备协作时配置容易丢失
  - **理论 GMV 预估与实际产出偏差大，影响决策**

## 3. 核心功能模块

### 3.1 数据上传与解析

支持上传四个文件：

| 文件 | 必填 | 说明 |
|---|---|---|
| 直播排期表 | 是 | 运营提供的周度排期 Excel，包含直播名、时间、时段、负责人、伪直播剔除信息 |
| 用户量级表 | 否 | 各品类各时间段的存量用户数（若排期文件中已包含可跳过） |
| 跨科偏好数据 | 否 | `转继承添加好友月份-公海品类-跨科品类-跨科率_直播间-转化率_直播间-LTV_直播间`（含 cohortMonth） |
| **4月直播明细表** | **否** | **历史实际直播数据：公开课名称、品类、曝光人数、总gmv、首单订单数、首单转化率。用于校准 GMV 预估模型。** |

系统自动识别文件类型并解析。排期表支持多 sheet（当前 sheet + 历史 sheet 自动追溯）。

**跨科偏好表格式**：
```
| 转继承添加好友月份 | 公海品类 | 跨科品类 | 跨科率_导量 | 转化率_导量 | LTV_导量 | 跨科率_直播间 | 转化率_直播间 | LTV_直播间 |
| 2026-03 | 普拉提 | 瑜伽 | 0.0000% | ... | ... | 0.0030% | 100.00% | 880.00 |
```
系统优先使用 `_直播间` 数据，为0时 fallback 到 `_导量` 数据。

**4月直播明细表格式**：
```
| 公开课名称 | 直播品类 | 直播状态名称 | 是否新用户测试直播 | 曝光人数 | 总gmv | 首单贡献占比 | 首单订单数 | 首单转化率 |
```
解析逻辑：
- 剔除 `是否新用户测试直播 = '是'` 和 `直播状态名称 = '回放'` 的行。
- 品类映射：优先使用「直播品类」列；若为空，从「公开课名称」推断。
- **数字清洗（v2.3 修复）**：支持 `¥35,000`、`12,500` 等带货币符号/千分位逗号的格式，自动清洗后解析。
- 按标准品类聚合计算 `avgGMV`、`avgExposure`、`avgFirstOrders`、`avgConversionRate`、`avgContributionRatio`。

**完成版排期解析**：
- 支持解析运营已确认的实际执行排期（正确版排期）
- audience 分配数据以多行形式嵌入在直播名下方
- 健康线 / 变美线 / 兴趣线 audience 可能跨多行，仅首行带线级标签
- 解析器连续收集同一线级的所有行，按列合并后提取 `(品类, 人数, 时间范围)`
- 跳过 Excel 时间数字（如 `0.291666666666667`）、纯标签行（如 `【晚间】`）、资源位标注（如 `不回捞`）
- 自动识别 `【上次直播排期】` 段落，将对应 audience 标记为伪直播历史记录（本周全局剔除）
- **容错处理**：若 `【上次直播排期】` 的 audience 分配行出现在直播信息行之前（排期表中顺序不固定），解析器会自动创建一个 `type: 'fake'` 的占位直播对象来接收这些 audience 数据，确保全局剔除逻辑不丢失

### 3.2 智能排期引擎（Auto-Scheduling Engine）

上传数据后，系统自动执行 audience 分配。

#### 3.2.1 直播解析规则

**早间晨练（联合直播）**：
- 同单元格内多行直播名 = **一场联合直播**，共享 audience 池
- 多行以换行符 `\n` 分隔，过滤掉时间、备注、空行
- 提取所有子品类：`name.replace('晨练', '').strip()`
- 联合直播名称用 ` + ` 连接所有子直播名
- 主品类 = 第一场直播的品类；线级 = 涉及的所有子品类线级去重
- 目标曝光 = 第一场子直播完整目标 + 后续子直播目标 × 0.5

**晚间专场**：
- 每行独立为一场单直播
- 通过关键词或前缀推断品类

**伪直播复用**：
- 伪直播标注的是 **上周实际使用的 audience**，本周仅作记录和全局剔除
- 伪直播本身 **本周不分配任何新 audience**

#### 3.2.2 目标曝光（Target Exposure）

| 评级 | 单直播目标曝光 |
|---|---|
| S | 350,000 |
| A | 220,000 |
| B | 150,000 |
| C | 120,000 |

联合直播目标 = 第一场子直播完整目标 + 后续子直播目标 × 0.5
> 举例：逆龄女神瑜伽(A) + 五禽戏晨练(B) = 220,000 + 150,000×0.5 = **295,000**

#### 3.2.3 动态目标缩放（v2.3 新增）

**问题**：不同周次的排期品类组合不同，按历史 avgGMV 直接加总可能导致周总预估偏离 20–25w 运营目标。

**解决**：
1. **原始预估** `weeklyRawTarget = Σ(当周各 real live 对应品类的 avgGMV)`
2. **缩放系数** `scaleFactor`：
   - `weeklyRawTarget > 250,000` → `scaleFactor = 250,000 / weeklyRawTarget`
   - `weeklyRawTarget < 200,000` → `scaleFactor = 200,000 / weeklyRawTarget`
   - 200,000–250,000 之间 → `scaleFactor = 1`
3. **校准后周目标** `weeklyScaledTarget = weeklyRawTarget × scaleFactor`

单场预估 GMV = 品类 `avgGMV × scaleFactor`，按 audience count 比例分摊到各 segment。

#### 3.2.4 品类规范化与同品类族判断

**规范化（normalizeCategory）**：
所有使用品类名做匹配的地方 **必须先经过 `normalizeCategory`**。

匹配优先级：
1. 精确匹配标准名
2. 精确匹配别名
3. 提取分隔符前前缀匹配（`-`、`—`、`|`、`·`、`•`）
4. 最长子串匹配标准名
5. 最长子串匹配别名

**同品类族判断**：
- **规则**：只有当 `normalizeCategory(a) === normalizeCategory(b)` **严格相等**时，才算同品类族
- **已废弃**：子串匹配、家族关键词匹配、前缀包含匹配均不再适用
- 典型反例：`君合太极` ≠ `太极BCD`，`一杰瑜伽` ≠ `瑜伽BCD`，`体态塑形瑜伽` ≠ `瑜伽SA`

#### 3.2.5 线级与跨线分配规则

- **默认规则**：同线分配（health → health，beauty → beauty，interest → interest）
- **联合直播**：自然跨线（涉及多线品类即可跨线）
- **单直播跨线**：只允许 **beauty 线 → health 线**，且仅限 **中性品类**
  - 中性品类：`一杰瑜伽`、`东方养正瑜伽`
- **禁止跨线**：health 线和 interest 线 **不向外跨线**

#### 3.2.6 Audience 复用约束（硬规则）

| 规则 | 说明 |
|---|---|
| 默认 1 次/周 | 同一 audience 段默认一周内只能触达 **1** 场直播 |
| 3 天间隔 | 未达目标的直播允许复用，同一 audience 段两次分配间隔 `>= 3` 天 |
| 一周最多 2 次 | 同一 audience 段一周内最多被分配 `2` 场直播（含 transfer） |
| 当日去重 | 同一天同一 audience 段只能分配给 **一场** 直播 |
| 跨科直播不能宣发同品类族 | `isCrossCategory === true` 时不能分配同品类族 audience |

**实现机制（`assignedDates`）**：
- 每个 `AudienceSegment` 维护 `assignedDates: string[]`，记录当前周被分配的日期
- **Round 1（严格分配）**：只选取 `assignedDates.length === 0` 的段，确保每段优先只使用一次
- **Round 2（refill）**：仅对 `exposure < target` 的直播，允许选取已使用一次的段，但要求 `daysBetween(assignedDates[0], live.date) >= 3`
- 手动拖拽调整时，`assignAudience()` 与 `removeAudience()` 同步维护 `assignedDates`

#### 3.2.7 自动排期算法

**直播优先级排序**：
```
score = GRADE_SCORE[grade] + slot_bonus + fake_hist_bonus + historical_gmv_bonus
GRADE_SCORE = {'S': 100, 'A': 70, 'B': 40, 'C': 20, null: 10}
slot_bonus: evening +50, morning +30, other +10
fake_hist_bonus: fakeLiveHistory.conversionRate × 100
historical_gmv_bonus: min(avgGMV / 20,000, 5)   // 封顶 +5
```
按 score 降序排列：真直播 S > 真直播 A/B/C > 伪直播。**历史产值高的直播获得额外加分**。

**伪直播预处理**：
- 收集所有 `type === 'fake'` 直播的 `assignedAudiences`，标记为全局已使用（`seg.status = 'used'`），确保本周不再分配
- 若排期表中 `【上次直播排期】` 的数据出现在直播信息行之前（顺序不固定），解析器会自动创建占位伪直播对象接收 audience 数据，避免全局剔除遗漏

**候选池过滤**：
1. **线级匹配**：`seg.line in allowed_lines`
2. **状态可用**：`seg.status != 'used'`
3. **次数限制**：`len(seg.assigned_dates) < 2`
4. **当日去重**：`live_day not in seg.assigned_dates`
5. **3天间隔**：`all(abs(live_day - d) >= 3 for d in seg.assigned_dates)`
6. **非同品类族**：`not any(isSameCategoryFamily(seg.category, cat) for cat in excluded_cats)`

**候选排序（7级优先级，高到低）**：
1. **同品类族优先**（垂类 audience 无需跨科，crossRate = 1.0）
2. **已分配品类去重**（避免同一品类重复选取，强制分散搭配）
3. **已分配 timeRange 去重**（同一时间段只选一次，进一步分散）
4. **超大段降权**（超过目标 60% 的段降低优先级，避免 greedy 独吞大池）
5. **已学习的规则匹配优先**（用户手动确认过的搭配，详见 §4.1）
6. **预估 GMV 降序（历史数据口径）**：
   - **有历史数据时**：`count × (avgGMV / avgExposure)`，即每触达一人的历史产值效率
   - **无历史数据时回退**：`count × crossRate × LTV`
7. **count 降序**

**停止条件**：达到目标曝光的 **130%** 后停止，确保每场直播能分配到 2–4 个段。

#### 3.2.8 历史等级推荐（v2.3 新增）

基于所有有历史数据品类的 `avgGMV` 计算四分位数，自动推荐等级标签。

**计算方式**：
1. 提取所有品类的 `avgGMV`，排序。
2. 计算 p20、p50、p80 分位数。
3. 每个品类的推荐等级：
   - `avgGMV >= p80` → **历S**
   - `avgGMV >= p50` → **历A**
   - `avgGMV >= p20` → **历B**
   - 其他 → **历C**

**展示位置**：直播卡片右上角，当前等级标签左侧。仅当推荐等级与当前等级不一致时显示。

**作用**：仅为建议，不自动覆盖 `categoryGrades`。运营可据此手动调整品类评级。

### 3.3 手动校准与拖拽调适

运营可以在看板上做以下调整：

- **历史记忆（nameOverrides）**：修改后可选择"保存并记住（按直播名）"，下次上传同名直播自动应用品类/线级

### 3.4 智能推荐面板（Smart Recommendation Panel）

左侧「智能推荐」区（需先选中一场直播）：

- 基于当前直播品类，筛选所有可跨科的 audience 品类
- **有历史数据时**：按 `预估GMV = 库存 × (avgGMV / avgExposure)` 降序排列（每触达一人的历史产值效率）
- **无历史数据时回退**：按 `预估GMV = 库存 × crossRate × LTV` 降序排列
- **cohort-aware**：优先按 audience.timeRange 的结束月份匹配 crossPref.cohortMonth，找不到则 fallback 全量平均
- 同品类族（垂类）高亮蓝色背景
- 显示 cohortMonth、crossRate、LTV、库存量级
- 直播间数据为0时，fallback 到导量数据，标灰提示
- 点击卡片直接分配，支持拖拽到直播卡片

### 3.5 排期归因看板（Attribution Panel）

全局归因弹窗，展示所有直播的数据归因。

**数据口径（v2.3 历史数据优先）**：

当上传了 4 月直播明细表（`categoryHistoricalStats` 非空）时，**所有 real live 统一使用历史口径**：

| 字段 | 有历史数据的品类 | 无历史数据的品类 |
|---|---|---|
| 触达人数 | Σ(audience.count) | Σ(audience.count) |
| 预计线索 | `(avgFirstOrders / avgConversionRate) × scaleFactor` | `0` |
| 预计首单 | `avgFirstOrders × scaleFactor` | `0` |
| 预计 GMV | `avgGMV × scaleFactor` | `0` |

**无历史数据时回退到理论模型**：
```
expectedLeads      = Σ(audience.count × crossRate)
expectedFirstOrders = Σ(expectedLeads × conversionRate)
expectedGMV        = Σ(expectedFirstOrders × ltv)
```

**归因匹配逻辑**（理论模型下）：
1. `fromCategory == audCat && toCategory == liveCat && cohortMonth == extractCohortMonth(aud.timeRange)`（精确匹配）
2. `fromCategory == audCat && toCategory == liveCat`（全量平均 fallback）
3. 默认 zero

**面板展示**：
- 支持按线级筛选（健康/变美/兴趣）
- 支持点击直播名跳转到详情面板
- Footer 显示「本周动态目标」和「缩放系数」
- 总触达人数**仅统计真直播**（`type === 'real'`）

### 3.6 导出 Excel

一键导出排期结果到 Excel，格式与运营现有模板兼容：

## 4. 智能体板块（Agent Features）

> 本系统已集成的 AI / 自动化智能体能力。

### 4.1 规则学习智能体（Rule Learning Agent） ✅ 已上线

**能力描述**：
当运营通过拖拽或点击手动调整 audience 分配时，系统弹出反馈弹窗，记录调整原因并沉淀为结构化规则。下次自动排期时，智能体优先应用这些规则。

**工作流程**：
1. 用户拖拽/点击分配 audience → 触发 `recordAdjustment()`
2. 弹出 `AdjustmentFeedbackModal`，展示调整前后的 GMV 对比
3. 用户输入调整原因（如"中医变美跨科率太低，瑜伽更匹配"）
4. 点击「确认并记录规则」→ 存储到 `learnedRules`

**规则结构**：
```typescript
interface LearnedRule {
  id: string
  liveCategory: string    // 直播品类（规范化后）
  fromCategory: string    // 被替换的 audience 品类（如有）
  toCategory: string      // 新分配的 audience 品类
  reason: string          // 用户输入的自然语言原因
  timestamp: number
}
```

**自动排期时的应用**：
在 `getCandidates()` 的 7 级排序中，第 5 级为「已学习的规则匹配优先」：
```typescript
const aRuleBoost = getRuleBoost(live.category, a.category)  // 匹配该直播品类+候选品类的规则数
const bRuleBoost = getRuleBoost(live.category, b.category)
if (aRuleBoost !== bRuleBoost) return bRuleBoost - aRuleBoost
```
匹配规则越多，候选 audience 的优先级越高。

**持久化**：
- localStorage（`schedule.learnedRules`）
- **Cloud Sync**：通过 Supabase 云端同步，多设备共享

### 4.2 智能排期引擎（Auto-Scheduling Engine） ✅ 已上线

**能力描述**：
完全自动化的 audience 分配引擎，在满足所有硬约束（频控、线级、同品类族）的前提下，按 7 级优先级为每场直播匹配最优 audience 组合。

**核心智能特性**：
- **联合直播自动合并**：同单元格多行直播自动识别为联合直播，共享 audience 池
- **cohort-aware 匹配**：按 audience 的 cohortMonth 精确匹配跨科率，而非使用全量平均值
- **动态目标计算**：联合直播目标 = 第一场完整目标 + 后续 × 0.5
- **强制分散策略**：通过「已分配品类去重」+「已分配 timeRange 去重」+「超大段降权」，确保每场直播分配到 2–4 个段
- **历史数据驱动（v2.3）**：
  - 直播排序引入历史 avgGMV 权重（封顶 +5 分）
  - 候选排序引入历史 ROI（avgGMV/avgExposure）
  - 归因统一使用历史口径，无历史数据品类归零
- **自我验证**：排期完成后自动运行 `validateSchedule()` 检查冲突

### 4.3 品类归一化引擎（Category Normalization Engine） ✅ 已上线

**能力描述**：
自动将 Excel 中各种变体/别名/带人名的直播名归一化到 69 个标准品类名，确保跨表数据联动时品类匹配正确。

**处理链路**：
```
"古法居家姚国诚" → normalizeCategory → "古法居家养生"
"睡眠-五禽戏" → normalizeCategory → "睡眠调理"
"面部驻颜瑜伽" → normalizeCategory → "面部瑜伽驻颜"
```

**技术实现**：
- 69 个标准品类 → 线级映射（`CATEGORY_TO_LINE`）
- 150+ 个别名映射（`CATEGORY_ALIASES`）
- 5 级匹配策略：精确匹配 → 别名匹配 → 前缀提取 → 子串匹配标准名 → 子串匹配别名

### 4.4 完成版排期解析器（Completed Schedule Parser） ✅ 已上线

**能力描述**：
自动解析运营已确认的实际执行排期表，提取其中嵌入的 audience 分配数据，用于：
1. 校准自动排期结果
2. 提取伪直播历史 audience（`【上次直播排期】`）
3. 验证规则正确性

**智能识别能力**：
- 自动识别「健康线/变美线/兴趣线」标签行及其后续无标签行
- 自动跳过 Excel 时间数字、资源位标注、空行
- 自动识别 `【上次直播排期】` 关键字，将对应 audience 路由到伪直播
- 支持跨多行的连续 audience 数据合并

### 4.5 云端同步智能体（Cloud Sync Agent） ✅ 已上线

**能力描述**：
基于 Supabase 的实时云端同步，确保配置（品类评级、线级覆盖、直播名记忆、学习规则、历史统计数据）在多设备间永不丢失。

**技术实现**：
- Supabase Realtime：`postgres_changes` 订阅，数据变更时自动刷新
- 自动保存：状态变更后 800ms 防抖自动触发云端保存
- 离线 fallback：未配置云端时，自动降级到 localStorage
- 防覆盖策略：`deserializeState` 时与 `DEFAULT_CATEGORY_GRADES` / `DEFAULT_CATEGORY_LINES` 做合并，避免空云端状态覆盖默认值

**同步范围**：
- 直播场次、audience 段、历史记录
- `categoryGrades`（品类评级）
- `categoryLines`（品类线级覆盖）
- `nameOverrides`（直播名记忆）
- `learnedRules`（学习规则）
- `gmvMultiplier`（GMV 校准系数）
- `categoryHistoricalStats`（历史统计数据，v2.3 新增）

### 4.6 历史记忆智能体（Historical Memory Agent） ✅ 已上线

**能力描述**：
按直播名持久化品类/线级配置，下次上传同名直播时自动应用，减少重复劳动。

**工作流程**：
1. 用户在 CategoryManager 或详情面板修改直播品类/线级
2. 点击「保存并记住」→ 调用 `setNameOverride(live.name, category, line)`
3. 数据持久化到 `nameOverrides`（localStorage + Cloud Sync）
4. 下次上传排期表时，`applyNameOverrides()` 自动扫描并应用

## 5. 数据格式规范

### 5.1 排期表结构（矩阵式）

```
| 星期 |      | 周一 | 周二 | ... |
| 日期 |      | 4/27 | 4/28 | ... |
| 早间 |
|      | 健康线 | 直播信息 | ... |
|      | 变美线 | 直播信息 | ... |
|      | 兴趣线 | 直播信息 | ... |
|      | 文案负责人 | 负责人名 | ... |
|      | 定时负责人 | 负责人名 | ... |
|      | 曝光量级 | 数字 | ... |
| 晚间 |
| ...（同上） |
```

直播信息单元格格式（多行文本）：
```
直播名称
开播时间：07:30-09:00
预约链接：xxx
```

### 5.2 Audience 量级表结构

```
| 线 | 品类 | 时间 | 用户数 | 时间 | 用户数 | ... |
| 健康线 | 睡眠调理 | 2025.1-2026.4 | 120000 | 2024.7-2024.12 | 80000 | ... |
```

**注意**：时间列是一个时间段（如 `2025.1-2026.4`），系统提取结束月份（`2026-04`）作为 cohortMonth 去匹配跨科偏好数据。

### 5.3 跨科偏好表结构

```
| 转继承添加好友月份 | 公海品类 | 跨科品类 | 跨科率_导量 | 转化率_导量 | LTV_导量 | 跨科率_直播间 | 转化率_直播间 | LTV_直播间 |
| 2026-03 | 睡眠调理 | 中医变美 | 0.15 | 0.08 | 200 | 0.12 | 0.10 | 220 |
| ... |
```

- **第0列**：`转继承添加好友月份`（如 `2026-03`），系统提取为 `cohortMonth`
- **公海品类**：audience 的品类（fromCategory）
- **跨科品类**：直播的品类（toCategory）
- **数据优先级**：`_直播间` 列优先；如果为0，fallback 到 `_导量` 列

### 5.4 4月直播明细表结构

```
| 公开课名称 | 品类 | 直播状态名称 | 是否新用户测试直播 | 曝光人数 | 总gmv | 首单贡献占比 | 首单订单数 | 首单转化率 |
| 八段锦晨间带练 | 八段锦 | 直播中 | 否 | 150000 | 35000 | 0.08 | 45 | 0.12 |
| ... |
```

- **公开课名称**：直播名称，用于品类推断（当「品类」列为空时）
- **品类**：标准品类名（优先使用此列做映射）
- **是否新用户测试直播**：填「是」的行会被剔除
- **直播状态名称**：「回放」状态的行会被剔除
- **总gmv / 曝光人数 / 首单订单数 / 首单转化率**：用于计算品类历史均值

## 6. 用户流程

```
1. 打开看板 → 点击「上传本周数据」
2. 上传排期表（必填）
3. 上传 audience 量级表（可选）
4. 上传跨科偏好数据（可选，需包含 cohortMonth 列）
5. 上传 4月直播明细表（可选，用于历史数据校准）
6. 点击「上传并生成排期」
7. 系统自动解析 + 历史数据校准 + 自动排期
8. 在看板上查看排期结果
   - 左侧：智能推荐 + 全部人群库存树
   - 中间：直播卡片列表（含历史等级推荐标签）
   - 右侧：选中直播的详情面板
9. 拖拽/点击调整 audience 分配
10. 输入调整原因，智能体记录规则（learnedRules）
11. 点击「排期归因」查看全局归因数据（动态目标 + 缩放系数）
12. 确认无误后点击「导出 Excel」
```
